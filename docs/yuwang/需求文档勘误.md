# 需求文档勘误

> 日期：2026-08-28
> 针对：`基于Foxglove Web插件实现ROS2 Bag回放调试方案（替代桌面版）.docx`、
> `Foxglove Studio ROS2 Bag回放调试界面设计.docx`
> 用途：这两份文档的调试思路（4 分区布局、蛇形/漂移故障判读、慢速回放流程）是对的，
> 直接照抄的**命令、包名、话题名和 JSON 格式**跑不起来。下面逐条给出实测结论和替代做法。

## 1. 工具链

| 文档写法 | 实测结论 | 替代做法 |
|---|---|---|
| `npm install -g @foxglove/studio-web` | 该包在 npm 上返回 404，不存在 | 正确路径是 Lichtblick release 里的 **`lichtblick-web.tar.gz` 预构建静态包**（v1.28.1，40 MB，解压出 403 个文件，即用）。**不需要 npm、不需要构建、不需要 Docker。** 本仓库已用 `fetch_lichtblick_web.sh` 固定该包并实测跑通 |
| `sudo apt install ros2-humble-rosbridge-suite`，连 `ws://localhost:9090` | 包名有误（应为 `ros-humble-rosbridge-suite`）；且本机 9090 端口被 `mihomo` 占用 | 本机已装 `foxglove_bridge` 3.4.3，端口 8765。Foxglove 原生支持它，**不需要 rosbridge** |
| `https://studio.foxglove.dev` 在线端 | 需要 Foxglove 账户，且数据要经过公网服务 | 项目约束是完全离线、自托管、无账户，因此不进入运行链路 |
| Web 端"与桌面 100% 一致" | 没有本项目实测依据；实际差异在**文件访问**上：网页端打不开 NX 上的 Bag 文件，浏览器只能读用户自己选的本地文件 | 不影响本项目 —— `foxglove_demo.sh play` 把 Bag 经 bridge 播成实时流，操作员不需要拿到文件本身 |

### WebSocket 子协议（重要）

`foxglove_bridge` 3.4.3 协商的子协议是 **`foxglove.sdk.v1`**。
用大多数文档仍在引用的 `foxglove.websocket.v1` 握手会被服务端回 `HTTP/1.1 400 Bad Request`。
`robot/script/robot/foxglove_ws_probe.py` 两个都提供，由服务端挑。

## 2. 话题名

文档里的话题名大多不是本仓库的真实名称。对照表：

| 文档写法 | 本仓库真实话题 | 类型 |
|---|---|---|
| `/ukf/odometry` | `/odom/localization_odom`（定位输出）、`/odom/nav2`（Nav2 实际消费） | `nav_msgs/msg/Odometry` |
| `/odom` | `/odom/mc_odom`（底盘，约 94～100 Hz） | `nav_msgs/msg/Odometry` |
| `/scan_cloud` | `/front_lidar` | `sensor_msgs/msg/PointCloud2` |
| `/ndt_pose` | `/localization/scan_match_pose` | `geometry_msgs/msg/PoseStamped` |
| `/rtk/pose` | `/rtk_pvh` | `robots_dog_msgs/msg/UniRtkPvh` |
| `/nav2/planner/plan` | `/plan` | `nav_msgs/msg/Path` |
| `/nav2/local_plan` | `/transformed_global_plan` | `nav_msgs/msg/Path` |
| （无） | `/cmd_vel_raw` → `/cmd_vel` | `geometry_msgs/msg/Twist` |
| （无） | `/status` | `localization/msg/ScanMatchingStatus` |
| （无） | `/localization_info` | `robots_dog_msgs/msg/Localization` |

补充两点，文档没写但对蛇形诊断是必要的：

- **`/odom/nav2` 不是 `/odom/localization_odom` 的转发。** `tf_publisher` 会先把 roll/pitch
  压平（yawOnly）再发布，而 `navigo_params.yaml` 里 `planner_server` 和 `controller_server`
  都指向 `/odom/nav2`。它才是 Nav2 真正消费的位姿，只看 `/odom/localization_odom`
  解释不了 Nav2 的行为。
- **`/cmd_vel_raw` → `/cmd_vel` 之间跨了 `collision_monitor`。** 两者的差就是安全层的干预量。
  这是区分"控制器自己在震荡"和"被安全层反复截断"的直接证据。

## 3. Bag 格式

| 文档写法 | 实测结论 |
|---|---|
| "直接本地打开 `.db3`，不需要 `ros2 bag play`" | 标准消息可以；**自定义消息不行**。`.db3` 不携带消息定义，`robots_dog_msgs/UniRtkPvh`、`localization/ScanMatchingStatus` 在宿主里无法解码 |
| 以 `.db3` 作为交付物 | 单个孤立 `.db3` 不是合格输入。rosbag2 目录必须包含 `metadata.yaml`；本机 `20260828_122342_indoor_patrol_diag` 就因缺 metadata 而 `ros2 bag info` 失败 |

**正确做法**：源 Bag 保留原样，另外用 `ros2 bag convert` 生成 MCAP 派生物给宿主用。
MCAP 会把 schema 内嵌，自定义类型才能解码，同时带索引、支持快速 seek。
本仓库 `mapping_rosbag.sh` 自 commit `e434175` 起已直接录制 MCAP + zstd。

实测：`20260808_002131_smoke_test`（SQLite3，2153 条）转 MCAP 后消息数一致，
源目录以 `READ_ONLY` 打开、未被改写。

## 4. 布局 JSON 格式

文档第四节给的 JSON **不是 Foxglove 布局格式**，导入会失败。具体问题：

| 文档写法 | 实际格式 |
|---|---|
| 顶层 `{"layout": {"direction", "children": [...]}}` | 顶层是 `{"configById": {...}, "layout": {...}}`；`layout` 是二叉 mosaic 节点 `{"first", "second", "direction", "splitPercentage"}`，只有两个子节点，没有 `children` 数组 |
| 面板用 `{"type":"panel","id":"scene_view","panelType":"Scene"}` | 面板 id 本身就编码类型，形如 `"3D!navscene"`；配置放在 `configById` 里以该 id 为键 |
| `"panelType": "Scene"` | 3D 面板的类型名是 `3D`，没有 `Scene` |
| `"panelType": "PlaybackControls"` | **不存在这个面板。** 回放控制是宿主自带的界面组件，不是可摆放的 panel，因此"区域 1 顶部通栏"无需也无法在布局 JSON 里声明 |
| 3D 的 `"topics": [{"topic": "/tf", "visible": true}]` | 是对象不是数组：`"topics": {"/tf": {"visible": true}}` |
| Plot 的 `"paths": ["/a.b.c"]` | 是对象数组：`[{"value": "/a.b.c", "enabled": true, "timestampMethod": "receiveTime"}]` |
| RawMessages 的 `"topics": ["/a","/b"]` | RawMessages 一个面板只看一个路径：`"topicPath": "/a"`。要看多个就放多个面板 |
| Image 面板的 `"cameraTopic": "/a"`（不在原文档里，但旧版 Foxglove 文档普遍这么写） | 1.28.1 没有这个键。整个 Image 配置在 `imageMode` 下面：`{"imageMode": {"imageTopic": "/a", "calibrationTopic": "/a/camera_info"}}` |

已按真实格式重写为同目录的 `nav_debug_layout.json`、`demo_patrol_layout.json` 和
`nuscenes_demo_layout.json`。三者不只是结构自洽：已在 **Lichtblick 1.28.1 + 真实 Chromium**
里加载，各自声明的面板全部挂载、无错误卡片、无控制台错误，`foxglove_demo.sh verify` 可重复复现。
上面这张表里的每一条差异，都是"照文档写会导入失败"的实际原因。

**但最后一行是另一类错误，值得单独说。** 前面那些写法宿主会直接拒绝，一眼就知道错了；
`cameraTopic` 不会 —— **宿主不认识的键会被静默丢弃，面板照样挂载，然后自己去自动选一个话题**。
本项目实际中招过：两个 Image 面板都悄悄换成了 `/CAM_BACK_LEFT`，而"面板全部挂载"的检查
照样通过。所以「导入成功、界面看起来正常」并不代表布局配对了，改配置后必须核对面板标题上
显示的话题。`verify` 现在有两条专门针对这一类的断言（浏览器里断言 Image 面板显示的就是配的
那个话题；再加一条纯静态断言禁止顶层出现 `cameraTopic` 这类键），并且实测过"把 bug 放回去
会失败"。

## 5. User Script API

文档给的脚本用的不是 Foxglove User Script API：

| 文档写法 | 实际 API |
|---|---|
| `export function messageHandler(msg)` | `export default function script(event)` |
| `import { Message } from "@foxglove/studio"` | `import { Input } from "./types"` |
| `publish({topic, message})` | 无 `publish()`；用 `export const output` 声明输出话题，函数 `return` 值即为消息 |
| 输出到 `/debug/pose_error` | 输出话题必须以 `/studio_script/` 开头 |
| 未声明输入 | 必须 `export const inputs = [...]` |

已按真实 API 重写为 `pose_error_user_script.ts`。注意该文件**仍未在宿主中执行验证过**
（布局本身已验证，但 User Script 没单独跑过），且 User Script API 在不同宿主版本间会有差异。

## 6. 方案 2（私有化 Web 部署）：已实现

原需求文档的"方案 2：私有化 Web 插件部署"**已经做了**，但走法和文档设想的不一样，而且简单得多。

文档假设要自建 Lichtblick Web 离线镜像，涉及镜像 digest 锁定、CSP、扩展持久化、
大文件 Range 策略。实际上上游的 Docker 镜像本身就只是 `caddy file-server` 托管一个静态目录
（`Dockerfile` release stage：`COPY --from=build /src/web/.webpack ./`），
而那个目录 upstream 已经作为 `lichtblick-web.tar.gz` 直接发布了。所以：

| 文档设想 | 实际做法 |
|---|---|
| npm 安装 + 构建 | 下载预构建静态包，sha256 校验后解压 |
| Docker 镜像 + digest 锁定 | 无 Docker（本机也没装）。lock 文件锁 version/url/sha256 |
| 复杂的同源反代 | Python 标准库 `ThreadingHTTPServer`，约 400 行，无新依赖 |
| 手动导入布局 | 用上游自带的 `LICHTBLICK_SUITE_DEFAULT_LAYOUT_PLACEHOLDER` 注入，打开即用 |
| 大文件 Range 策略 | 不需要，见第 1 节：回放走 bridge 实时流，不走文件 |

实现落在 `fetch_lichtblick_web.sh` + `foxglove_web_serve.py`，入口是
`foxglove_demo.sh web`。三个实测中值得记下的坑：

1. **`.wasm` 必须显式声明 `application/wasm`。** Python 的 `mimetypes` 不认这个扩展名，
   MIME 错了浏览器会拒绝实例化 WASM，页面直接白屏。
2. **反向代理必须原样转发 `Sec-WebSocket-Protocol`。** 丢了这个头，
   `foxglove_bridge` 3.4.3 会回 400（见第 1 节的子协议说明），每个客户端都连不上。
3. **CSP/COOP/COEP 默认不开。** 上游自己的 Docker 镜像（caddy file-server）就没设，
   开了反而可能挡资源。留了 `--cross-origin-isolated` 开关备用。

本 MVP 现在覆盖：网页宿主 + 桌面宿主 + 只读 bridge + MCAP 回放 + 无真狗的数据源，
均已在本机实测通过（见 `FOXGLOVE_MVP_使用说明.md` 第 6 节）。
仍未做的是自定义 `.foxe` 扩展面板、平台 Vue 同源入口和性能基线，
见 `docs/superpowers/plans/2026-08-28-foxglove-web-ros2-bag-debugging.md` 的 M3/M4。
