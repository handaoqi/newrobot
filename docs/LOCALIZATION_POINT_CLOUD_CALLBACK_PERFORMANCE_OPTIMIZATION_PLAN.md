# 定位点云回调性能优化计划

## 1. 目标

解决定位节点点云输入 10 Hz、单帧处理长期超过 100 ms 所造成的队列积压、定位结果滞后和全局重定位期间长时间阻塞问题。

本计划的目标不是降低 Livox 原始点云的全局发布频率，而是：

- 保持 `/front_lidar` 为 FAST-LIO、激光避障和传感器健康监测提供约 10 Hz 数据；
- 保持 FAST-LIO 连续位姿更新约 10 Hz；
- 将稳定状态下的 NDT/VGICP 重型绝对匹配控制在约 2 Hz；
- 只处理最新的定位点云，不追赶已经过期的积压帧；
- 将同步全局重定位从实时点云回调链中隔离；
- 让定位输出在高负载和重定位期间保持可观测、可恢复。

## 2. 现场基线

2026-08-29 实机只读检查结果：

| 指标 | 当前值 |
|---|---:|
| `/front_lidar` 发布频率 | 约 10 Hz |
| 单帧点数 | 19,968 |
| 单帧消息大小 | 约 519 KB |
| 点云带宽 | 约 5.25 MB/s |
| 定位回调告警样本 | 2,794 |
| 告警覆盖时长 | 352.4 s |
| 实际回调处理速率 | 约 7.93 Hz |
| 回调耗时中位数 | 124 ms |
| 回调耗时 P99 | 约 186 ms |
| 当前日志最大值 | 247 ms |
| 历史异常值 | 300–900 ms，最严重约 1.46 s |
| 定位进程 CPU | 约 167% |
| 当前连续定位源 | `lio_imu` |
| 当前策略阶段 | `stationary` |

输入周期约为 100 ms，而回调中位耗时已经达到 124 ms，因此系统无法实时处理每一帧。当前订阅深度为 5，过载时还会继续处理旧帧，进一步扩大端到端定位延迟。

## 3. 根因分析

### 3.1 静止状态每帧执行 NDT/VGICP

当前 `motion_phase_` 默认和空闲状态均为 `stationary`。`moving_ndt_stride=5` 只限制移动状态；稳定静止时仍对约 10 Hz 的每帧点云执行 NDT，并按配置继续执行局部 FastVGICP refine。

当前系统已将 FAST-LIO 设为连续主源，NDT/VGICP属于间歇绝对校正源。稳定状态以 10 Hz 执行绝对匹配没有必要。

### 3.2 NDT降频判断发生在点云前处理之后

现有执行顺序为：

```text
ROS PointCloud2 转 PCL
  → 距离/FOV裁剪
  → 地面过滤
  → 0.15 m体素滤波
  → 坐标变换
  → 判断本帧是否执行NDT
  → NDT + FastVGICP
```

因此移动状态下即使只有每 5 帧执行一次 NDT，其余帧仍承担了完整的点云转换和前处理开销。

### 3.3 订阅QoS会保存积压帧

定位节点使用默认 Reliable、`KeepLast(5)` 订阅 `/front_lidar`，而 Livox发布端为 Best Effort。实时传感器处理不应追赶旧帧，应使用与发布端一致的 SensorData QoS，并只保留最新帧。

### 3.4 全局重定位同步占用点云回调

Scan Context候选验证和全局 ICP直接在 `points_callback` 中同步执行。定位节点又使用单线程执行器，因此一次 1秒级全局重定位会同时阻塞：

- 后续点云；
- 定位状态发布；
- 里程计定时器；
- 初始化/重定位服务；
- 其他同节点回调。

历史 300 ms至1.46 s尖峰最可能来自这一同步路径。实施前需要增加分阶段耗时统计进一步确认。

### 3.5 当前耗时指标并非完整回调耗时

现有 `last_timeout_` 在 aligned point cloud转换、位姿历史更新、决策发布和里程计发布之前停止计时。因此日志中的回调耗时可能低估完整执行时间。

## 4. 设计原则

1. 不全局降低 `/front_lidar` 频率，避免影响 FAST-LIO和避障。
2. 优先减少重型匹配次数，而不是停止连续 LIO位姿更新。
3. 实时链路只处理最新帧，不处理已经失去实时价值的历史点云。
4. 初始化、稳定运行、定位恢复采用不同频率策略。
5. 所有点云和配准参数修改必须经过 rosbag A/B回放，不直接在运动中的真机试调。
6. 先建立分阶段耗时指标，再调整体素、迭代次数等精度相关参数。

## 5. 分阶段实施

### 阶段0：建立可量化性能基线

修改定位节点的性能统计，将回调拆分为：

- 等待锁耗时；
- PointCloud2转PCL；
- 距离/FOV/地面过滤；
- 体素降采样与坐标变换；
- LIO观测应用；
- NDT coarse；
- 局部地图裁剪；
- FastVGICP refine；
- 全局重定位；
- aligned cloud转换与发布；
- 完整回调总耗时；
- 消息到达年龄和丢弃数量。

统计采用固定周期汇总，避免逐帧日志进一步增加负载。输出至少包含 count、mean、P50、P90、P99和max。

### 阶段1：消除旧帧积压

将点云订阅调整为：

```cpp
auto qos = rclcpp::SensorDataQoS().keep_last(1);
```

并增加点云年龄保护：

- 正常稳定阶段：消息年龄超过 200 ms直接丢弃；
- 初始化和主动重定位阶段：只保存最新候选帧，不连续处理积压帧；
- 记录 `cloud_dropped_stale` 和 `cloud_replaced_by_latest`。

该阶段不改变匹配频率和配准参数，用于单独验证QoS与丢帧行为。

### 阶段2：提前进行重型分支判定

把是否需要点云转换/NDT的判断移动到 `pcl::fromROSMsg` 之前。

建议定义：

```text
needs_heavy_cloud =
  未完成初始化
  或主动/全局重定位已请求
  或FAST-LIO不新鲜，需要点云里程计回退
  或本帧命中NDT调度周期
```

当 `needs_heavy_cloud=false` 时：

- 应用最新 FAST-LIO观测；
- 更新定位源、稳定性和状态；
- 发布轻量位姿结果；
- 不进行PCL转换、地面过滤、体素滤波、NDT和VGICP。

注意：不能简单从函数开头 `return`，因为当前 FAST-LIO观测是在点云回调中应用。若要真正降低函数进入次数，需要先把 FAST-LIO连续更新迁移到 LIO回调或独立定时器。

### 阶段3：统一稳定状态NDT频率

新增可配置参数：

```yaml
source_arbiter:
  moving_ndt_stride: 5
  stationary_ndt_stride: 5
  initialization_ndt_stride: 2
```

以10 Hz点云为例：

| 状态 | FAST-LIO更新 | NDT/VGICP建议频率 |
|---|---:|---:|
| 正常移动 | 10 Hz | 2 Hz |
| 正常静止 | 10 Hz | 2 Hz |
| 初始定位 | 10 Hz | 5 Hz |
| 普通定位恢复 | 10 Hz | 2–5 Hz |
| 全局重定位 | 10 Hz连续源 | 单次后台任务 |

初始值先采用稳定状态2 Hz，依据漂移校正时延和几何验证结果再决定是否提高到3.3 Hz。

### 阶段4：隔离全局重定位

把 Scan Context和全局 ICP从实时点云回调中移到独立工作线程：

1. 点云回调只更新一个容量为1的最新帧邮箱；
2. 重定位请求以原子状态置位；
3. 后台线程复制最新降采样帧和必要地图快照；
4. 不持有 `pose_estimator_mutex` 执行昂贵的候选检索/ICP；
5. 完成后短时间持锁，验证结果仍适用于当前地图和恢复代次，再提交位姿；
6. 新请求覆盖旧请求，禁止积压多个全局重定位作业；
7. 发布重定位开始、候选、耗时、成功/失败和结果过期事件。

必须通过 generation ID防止旧地图或旧恢复周期的异步结果回写当前估计器。

### 阶段5：单帧计算优化

在阶段0数据证明瓶颈后，再依次进行A/B测试：

1. `points_voxel_filter_size`：0.15 m → 0.20/0.25 m；
2. `ndt_resolution`：0.15 m → 0.20/0.25 m；
3. `local_map_xy_radius`：18 m → 12–15 m；
4. `FastVGICP max_iterations`：20 → 10/15；
5. 局部地图按空间块缓存，避免每次遍历完整全局地图；
6. 没有订阅者时继续禁止 `/aligned_points` 转换发布。

不得同时修改多项精度参数，否则无法确认定位精度下降来自哪一项。

## 7. 测试计划

### 7.1 单元测试

- SensorData QoS为 Best Effort、深度1；
- 过期点云被丢弃；
- 稳定移动/静止状态命中正确stride；
- 初始化阶段保持较高匹配频率；
- LIO失效时强制恢复点云处理；
- 全局重定位同时最多一个作业；
- generation ID变化后旧结果不能回写；
- 跳过重型分支时LIO位姿仍连续更新。

### 7.2 rosbag回放A/B

至少覆盖：

- 室内静止60秒；
- 直线、转弯和原地旋转；
- 狭长走廊与重复几何区域；
- 短时点云中断；
- FAST-LIO短时失效；
- 错误初值后的主动重定位；
- Scan Context候选正确和错误场景。

比较指标：

- 完整回调P50/P90/P99/max；
- 点云消息年龄P99；
- 重型匹配频率；
- CPU和内存；
- NDT/VGICP fitness与inlier；
- 轨迹ATE/RPE；
- LIO到地图漂移校正时延；
- 定位丢失和误恢复次数；
- Nav2控制周期超时数量。

### 7.3 真机静态验证

真机保持不运动：

- 运行10分钟；
- 检查定位状态持续为3；
- 检查点云队列不增长；
- 检查重型匹配约2 Hz；
- 检查CPU和温度；
- 手动触发一次不带运动的定位恢复，验证后台作业和状态发布。

### 7.4 真机运动验证

仅在电量、温度、急停和现场安全条件满足并获得明确运动授权后执行：

- 低速短直线；
- 原地转向；
- 原三点路线；
- 定位短时退化后的自动恢复；
- 到点播报期间定位恢复。

## 8. 验收标准

### 性能

- 稳定运行时重型NDT/VGICP频率：`2.0 ± 0.3 Hz`；
- 点云消息年龄P99：小于200 ms；
- 轻量帧完整回调P99：小于30 ms；
- 重型匹配帧P99：小于200 ms；
- 稳定阶段不得出现连续队列追帧；
- 非全局重定位场景最大回调耗时：小于300 ms；
- 全局重定位不得阻塞实时定位输出超过200 ms；
- 定位节点平均CPU较基线下降至少30%。

### 定位质量

- 正常路线定位状态保持3；
- 相比基线，ATE/RPE不得显著恶化；
- 不增加错误关键帧匹配或错误全局位置接受；
- LIO漂移超过门限后，NDT校正仍能在规定窗口内触发；
- FAST-LIO失效时仍能进入点云回退和恢复流程；
- Nav2不得因定位输出中断产生新的目标拒绝或控制超时。

## 9. 回滚策略

所有新行为均由参数控制：

- 可恢复原QoS深度；
- 可关闭点云年龄丢弃；
- 可将各stride恢复为1；
- 可关闭异步全局重定位，恢复同步路径；
- 配准参数逐项恢复基线值。

每个阶段单独提交、单独回放验证。若定位质量或恢复成功率下降，只回滚当前阶段，不混合回滚其他已验证改动。

## 10. 实施顺序

1. 阶段0：完整性能统计；
2. 阶段1：SensorData QoS、深度1、过期帧丢弃；
3. 阶段2：提前重型分支判定；
4. 阶段3：稳定静止状态降至2 Hz NDT/VGICP；
5. 完成第一轮rosbag和静态真机验收；
6. 阶段4：异步全局重定位；
7. 阶段5：依据数据逐项优化体素、局部地图和迭代次数；
8. 完成原三点路线和定位恢复实机验收。
