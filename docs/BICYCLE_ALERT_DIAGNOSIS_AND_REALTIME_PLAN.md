# 自行车识别校正、照片诊断与三区告警实时同步方案

## 1. 审计结论

- 当前运行的是通用 COCO `yolo11n.onnx`，现场配置为置信度 `0.60`、输入 `512`、最小检测框面积 `2500 px²`、连续 `3` 帧确认、告警冷却 `10` 秒。
- 运行配置把 `person`、`bicycle`、`bike`、`自行车`作为模型输出类别表。COCO 输出中类别 2 为 car、类别 3 为 motorcycle，当前代码会将它们错误标为 `bike`、`自行车`，导致事件的真实类别失真。
- COCO 的 bicycle、car、motorcycle 分别是类别 1、2、3，三者都应归入“自行车告警”业务组，但必须保留实际 COCO 类别。手机照片无法识别还可能来自输入分辨率、置信度门限、最小面积门限。单张照片可通过模型门限也不等于触发实时告警，后者还要求连续三帧。
- 保安值守已订阅新事件并刷新列表与待处理数；监测中心订阅新事件但漏更新待处理数；远程控制只有人员跟随检测框，尚无自行车告警窗口和事件流订阅。

## 2. 模型与告警链路修正

1. 为通用 COCO YOLO 固定使用完整 80 类 canonical 类别表；模型类别索引必须与模型输出宽度一致。配置中的前四项明确为 `person`（0）、`bicycle`（1）、`car`（2）、`motorcycle`（3），不再使用 `bike`、`汽车`等非 COCO 输出名称。
2. 将 COCO 类别 1、2、3 的 `bicycle`、`car`、`motorcycle`统一归入“自行车告警”业务组；事件的 `object_class`、标注框和诊断结果保留实际类别，告警标题/处置流程仍使用自行车告警业务语义。
3. 进程启动时校验输出类别数和类别表长度；不一致时明确失败，禁止静默错标。
4. 保持置信度 `0.60`、3 帧确认及 10 秒冷却不变；将现场 `min_box_area` 从 `2500` 调整为 **`1600 px²`**，并通过照片诊断与现场回归确认效果后再决定是否继续调整或更换模型。

### 2.1 最小检测框面积调整依据

- 该门限在还原到原始视频帧后判断。现场帧为 `1280×720`，当前 `2500 px²`占原始画面约 `0.271%`，等效约 `50×50 px` 的正方形框。
- `1280×720` 以 letterbox 缩放至 `512×512`时，实际图像内容为 `512×288`，缩放系数为 `0.4`；`2500 px²`在模型输入中仅约为 `400 px²`，即约 `20×20 px`。
- 推荐值 `1600 px²`等效原始帧约 `40×40 px`，模型输入约 `16×16 px`；占原始画面约 `0.174%`。它比当前门限降低 36%，可接纳更小的手机照片/远景目标。
- 不低于 `1200 px²`：该值仅约 `35×35 px` 原始框、`14×14 px` 模型框。对通用 YOLO11n 而言，类别 1、2、3 同时进入告警业务组后，小框误检风险会明显上升。
- 该调整不能让模型凭空识别低清、反光、遮挡或在 512 输入中无有效 bicycle/car/motorcycle 候选的照片；照片诊断必须区分模型未检出、置信度不足和面积不足。

## 3. 事件中心照片识别测试

### 3.1 用户流程

1. 在事件中心新增“自行车照片识别测试”面板。
2. 操作员选择目标机器狗及本地图片；一次最多 20 张，只接收 JPG、PNG、WebP。
3. 机器狗使用**当前部署**的 Bike Bot、模型、Provider、输入尺寸和阈值逐张执行单帧诊断。
4. 页面轮询任务状态，并显示原图、标注图、最佳自行车告警业务组框及其实际类别、置信度、面积、模型/Provider 和具体判断结果。

### 3.2 诊断结果

每张图片必须归入以下一种结果，并显示实际命中的 `bicycle`、`car` 或 `motorcycle` 类别及适用门限：

- `passed_single_frame`：自行车告警业务组目标通过当前置信度与面积门限；
- `below_confidence`：模型有自行车告警业务组候选，但低于实时置信度门限；
- `below_min_box_area`：置信度合格，但检测框面积不足；
- `not_detected`：模型未输出自行车告警业务组候选；
- `failed`：下载、解码、模型或设备侧处理失败。

页面固定提示：单帧通过只说明具备实时检测基础；真实告警仍要求同一目标连续 3 帧命中。

### 3.3 隔离与数据流

- 单帧测试不得调用跟踪器、`BicycleAlertPolicy`、抓拍、语音、MQTT 或真实告警写入；不得影响现有冷却状态、告警条数、保安值守或监测中心。
- 平台新增临时测试任务和图片项，状态为 `queued`、`running`、`finished`、`failed`、`expired`。
- 新增认证后的运营端创建/查询接口，以及设备凭证专用的诊断任务拉取、原图下载、结果回传接口；不复用音频命令轮询通道。
- Bike Bot 新增低优先级诊断 worker，复用当前 `YoloDetector` 会话；推理锁保证实时视频检测优先。
- 任务超时为 120 秒。输入图、标注图和结果保留 24 小时后自动清理。

## 4. 三页面实时告警一致性

1. 建立共享前端告警状态 composable，统一订阅 `/events/stream/`，按机器人和事件 ID 去重，维护最近 5 条记录、今日告警数和待处理数。
2. 服务端除 `inspection_event_created` 外，在处理/归档事件后发送 `inspection_event_updated`；前端实时更新记录状态和待处理数量。
3. 共享状态每 30 秒回读一次概览与当前机器人详情，用于 SSE 重连后的最终纠偏。
4. 保安值守和监测中心迁移到该共享状态源；修复监测中心新告警未增加待处理数的问题。
5. 远程控制页在视频区域下增加“实时告警”窗口，显示当前选中机器狗的最新缩略图、标题、时间、最近记录及待处理数入口；不覆盖人员跟随检测框和遥控区。
6. 照片测试任务不进入事件流，绝不改变三个页面的真实告警记录与条数。

## 5. 验收与测试

- COCO 类别 1、2、3 分别解析为 bicycle、car、motorcycle；三者均进入自行车告警业务组，但事件和诊断结果必须保留各自真实类别。
- 覆盖四种单帧诊断结果、标注图、三帧状态不受测试影响、任务超时和设备失败回传。
- 覆盖事件中心的机器狗选择、批量 JPG/PNG/WebP 上传、状态轮询与 24 小时清理。
- 覆盖三页面收到同一新事件后的实时列表/计数更新、重复 SSE 去重、归档后的待处理数减少和切换机器狗后的过滤。
- 在 `1600 px²`下，现场使用近距离整车、侧面整车、局部车轮、小目标远景、汽车和摩托车照片逐张测试，确认类别 1、2、3 均进入业务告警组且标签正确。
- 回归实时视频：每类目标连续三帧才产生一条告警；无目标、人员、树木、地面纹理和远景噪声不得产生告警。若 `1600–2499 px²`新增目标主要是误检，则回退 `2500`；只有照片诊断证明大量有效目标仍因面积被拒绝且无误检时，才考虑下调至 `1200`。
- 再以结果决定后续是否恢复 640 输入、调整置信度或训练专用模型。
